# Disposable protected Render preview

Separate preview branch based on desktop 25dd6fd (approved mobile base 93f1ce2).
This is the real Next app, not a static export. No live payments or production launch.

## Proposed single-service settings

- Runtime: Node; Node version 22 (NODE_VERSION=22).
- Plan: Free; region: Singapore; automatic deploy: off.
- Branch: feature/hosted-demo-preview-20261022 (must be published before deployment).
- Build: npm ci --include=dev && npm run preview:build
- Start: npm run preview:start
- Health check: /preview-health
- No disk, external database, environment group or paid service.
- Render provides PORT; server binds 0.0.0.0.

Three distinct secrets of at least 32 characters must be approved/generated and
entered through the hosting secret configuration, never committed or printed:
PREVIEW_ACCESS_PASSWORD, PREVIEW_ACCOUNT_PASSWORD, SESSION_SECRET.
No secrets have been generated by this preparation.

The first browser prompt uses username preview and PREVIEW_ACCESS_PASSWORD.
After that, open /preview or use Switch preview role to choose Customer, Tradie
or Administrator without typing another password. The picker invokes the existing
normal password login for a fixed synthetic account; it does not create sessions
directly or accept arbitrary account identifiers.
The existing app login also supports customer@demo.test, sparky@demo.test or
admin@demo.test and PREVIEW_ACCOUNT_PASSWORD. These are fresh synthetic users,
not any local or real accounts. Share access only with intended reviewers.
All ordinary application authorization remains active behind the outer gate.
The shared sample-account password is suitable only for this gated disposable demo.

## Isolation and access

The start command fails closed without all three distinct secrets. It overrides
DATABASE_URL with a newly created temporary database every start, migrates and
seeds only that new database, and creates a separate temporary upload directory.
It never copies existing databases or uploads. Existing known demo passwords
are replaced by the supplied preview account secret. Local /demo shortcuts are
forced off. The /preview role switch is available only behind the outer gate.
Only built-in illustrative assets ship.

After initializing fresh isolated storage, the custom server generates a random
boot-only assertion held in process memory. It strips incoming assertion headers
and injects its own only after successful outer authentication. Both /preview
rendering and its action require the hosted flag plus that exact assertion.
Ordinary next start has no boot identity, so a spoofed header or environment flag
alone cannot enable role login. The assertion is not logged, returned to clients,
stored in the database or configured as another persistent secret. Restarting
changes it. Existing preview access/account/session secrets remain unchanged.

The Node HTTP gate precedes Next for every method and URL, including admin,
uploads, static assets and server actions. No Next middleware header bypass
skips it. Only the constant GET/HEAD /preview-health response is public.
WebSocket upgrades are rejected. Render must terminate HTTPS; Basic access
credentials must never be used on a public plain-HTTP endpoint. There is no
second unprotected Next listener. Do not start this deployment with next start.
App signup remains usable only after entering the outer access gate.

Free Render storage is ephemeral: edits and uploads reset on idle shutdown,
restart or redeploy. Build initializes a separate empty temporary schema, never
the local development database. Persistent storage is unnecessary for this
review, and would require a separate paid decision.

## Pre-publication checks

Run npm run preview:test, npm test, npm run lint, npm run typecheck,
and npm run preview:build. Exercise the actual custom server with test-only
secrets and an isolated temporary database: unauthenticated pages/actions/files
must be 401; health 200; authenticated app and normal login must work; /demo
must have no role controls. Confirm old demo-password fails. Verify restart
starts a fresh database. Test the deployed HTTPS URL from outside the Mac.
Also verify /preview rejects anonymous and spoofed requests, all three role
buttons reach the correct account, invalid roles fail, and ordinary next start
does not expose the picker even with a hosted flag and spoofed assertion.

Workspace confirmation, secret approval/configuration, source publication,
Render creation and external verification are separate remaining steps.
